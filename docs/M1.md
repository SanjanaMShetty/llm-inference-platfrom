# M1 verification: core operator

How to prove M1 is done. Each step says what you should see. Record the numbers; they go
into `experiments/m1-operator/README.md`.

## What M1 adds

New files: `api/`, `cmd/operator/`, `internal/controller/`, `config/` (CRD, RBAC, operator
manifest, samples, invalid samples), `Dockerfile.operator`, `hack/e2e-m1.sh`,
`hack/measure-ready.sh`, `hack/boilerplate.go.txt`, ADRs 0002-0004,
`experiments/m1-operator/`, this file.

Replaced files (they existed in M0; diff before overwriting if you changed them):
`Makefile` (M0 targets kept, M1 targets added), `Dockerfile` (Go version arg, no module
download), `.github/workflows/ci.yml` (envtest tests and a generated-files check).

Not touched: your M0 Go code, `README.md`, `CLAIMS.md`.

The code assumes the Go module is named `llm-platform`. If you renamed it, rewrite the
imports: `grep -rl 'llm-platform/' --include='*.go' . | xargs sed -i.bak 's#"llm-platform/#"<your-module>/#g'`.

## 0. First-time setup

This code was written without a Go toolchain, so the first build is also its first
compile. Expect to fix a typo or two. The pinned versions come from published releases:
controller-runtime v0.24.1 (with Kubernetes v0.36 libraries and Go 1.26),
controller-tools v0.22.0, setup-envtest v0.24.1.

```bash
make deps            # go get controller-runtime@v0.24.1 and go mod tidy; may raise the go directive
go version           # must satisfy the go directive now in go.mod; Go can auto-download a newer toolchain
make generate manifests   # replaces my hand-written deepcopy, CRD and RBAC with generated ones
git diff --stat      # review what changed, then commit it
gofmt -w .
go vet ./...
```

`make generate manifests` is the important step. The CRD and deepcopy file I shipped were
written by hand to match controller-gen's output; the Go markers in `api/` and
`internal/controller` are the source of truth. After you commit the generated files,
`make verify-generated` (and CI) will fail whenever someone forgets to regenerate.

If `make deps` or `go vet` report API errors from controller-runtime, paste them to me.
Newer releases than v0.24.1 exist; stay on the pinned one until M1 passes, then bump.

## 1. Unit tests (no cluster)

```bash
make test-unit
```

Expect `ok`. The integration tests print a loud `SKIPPED` warning. These tests cover the
object builders (selector, probes, per-backend containers, args, resources), the status
logic (every phase, ordering, truncation, idempotence), and replica-ownership detection.

## 2. Integration tests (real API server through envtest)

```bash
make test
```

The first run downloads the envtest binaries (kube-apiserver and etcd). Expect `ok` and no
skips. This runs, against a real API server:

- `TestAdmission`: 5 CEL rules and the schema constraints. Every bad spec is rejected with
  no reconciler running.
- `TestDefaultsAreApplied`, `TestAutoscalingDefaultsFillMissingBound`.
- `TestReconcileCreatesOwnedDeploymentAndService`: owner references, selector, probes,
  initial replicas, status, no finalizer.
- `TestReplicasAreOwnedByBootstrapNotByTheOperator`, `TestOperatorNeverFightsTheAutoscaler`.
- `TestBackendSwitchLeavesExactlyOneContainer`: vLLM, Ollama and fake in turn.
- `TestDriftIsCorrected`, `TestStatusPhases` (7 scenarios), `TestRestrictedVLLMReportsAcceleratorNotApplied`.
- `TestSteadyStateMakesNoEffectiveWrites`, `TestDeletionLeavesCleanupToGarbageCollection`,
  `TestApplyFailureIsReportedAndThenHeals`.
- `TestManagerWiring`: the real manager, proving the Deployment and Pod watches drive status.

If envtest fails to start with a CRD error, run `make manifests` and retry. If
`make test` cannot install setup-envtest at the pinned tag, run
`go install sigs.k8s.io/controller-runtime/tools/setup-envtest@latest` and set `ENVTEST_VERSION`.

## 3. Collect the numbers

```bash
make cover                                    # statement coverage
make test-run RUN=TestAdmission               # prints the CEL rule and negative-case counts
make test-run RUN=TestSteadyState             # API requests per reconcile in a quiet cluster
make test-run RUN=TestReconcileDurationReport # first-reconcile time and steady-state p50/p95
go test -v ./... 2>&1 | grep -c -- '--- PASS' # total test and subtest passes (needs KUBEBUILDER_ASSETS to include integration)
```

Expected: 5 CEL rules; 8 CEL negative and 7 schema negative cases; the steady state shows
2 apply requests, 0 status writes and unchanged resourceVersions per reconcile.

## 4. Run on kind

```bash
time make cluster        # record it
make load-image          # the fake backend image the operator will deploy
make install-crds
kubectl get crd inferenceservices.inference.llmplatform.dev
```

Start the operator in another terminal (fastest loop):

```bash
make run-operator
```

You should see `starting manager` and a controller start line.

## 5. See it work

```bash
kubectl apply -f config/samples/inferenceservice_fake.yaml
kubectl get llmsvc -w                   # Loading -> Ready
kubectl get deploy,svc,pods -l llm-platform.io/inference-service=demo-fake
kubectl get llmsvc demo-fake -o yaml    # status: phase, replicas, endpoint, conditions
```

Reject bad specs (the operator plays no part):

```bash
for f in config/samples/invalid/*.yaml; do kubectl apply --dry-run=server -f $f; done
```

Each of the six must fail with its own message.

Then run the scripted version of everything above, plus the failure phases:

```bash
make e2e
```

It checks admission, the healthy service (ownership, selector, one container, startup
probe sizing, real streaming traffic through the created Service), Degraded (bad image
while a replica serves), recovery, autoscaler ownership (`kubectl scale` then a spec change:
replicas must stay), Unschedulable (asks for 1000 CPUs; the scheduler's message must reach
status), Failing (missing image), and deletion garbage collection. It ends with `E2E OK`.

## 6. Run the operator inside the cluster

Stop `make run-operator`, then:

```bash
make operator-deploy
kubectl -n llm-platform-system get pods
kubectl -n llm-platform-system logs deploy/llm-platform-operator | tail
make e2e
```

## 7. Timing

```bash
make measure-ready RUNS=5
```

Prints apply-to-Ready for each run and the median, min and max. This includes scheduling,
the container start and the readiness probe. Record it with the operator both running
locally and in-cluster if you want to compare.

## 8. CI

Push. The `lint`, `test`, `generated` and `build` jobs must be green. `generated` fails
until you have committed the output of `make generate manifests`. Prove it is real: edit a
field comment in `api/v1alpha1/inferenceservice_types.go`, push without regenerating, and
confirm `generated` fails.

## Done when

| M1 acceptance criterion | Proved by |
|---|---|
| envtest suite covers create, update, backend switch, deletion, CEL rejections, field ownership | Step 2 |
| A bad spec is rejected by the API server even when the operator is not running | `TestAdmission`; Step 5 dry-run loop |
| Switching backend leaves exactly one serving container | `TestBackendSwitchLeavesExactlyOneContainer` |
| Operator never fights an autoscaler over replicas | `TestOperatorNeverFightsTheAutoscaler`; `make e2e` step 4 |
| Status reflects cluster reality, with scheduler/kubelet reasons | `TestStatusPhases`; `make e2e` steps 3, 5, 6 |
| Selector holds only the service name | `TestSelectorIsMinimal...`; `make e2e` step 2 |
| Measurements recorded (reconcile p50/p95, steady-state writes, test counts, coverage, CEL rules and negatives, apply to Ready) | Steps 3 and 7 |

## What I could not verify

I could not compile or run any of this. Specifically unchecked: that the code builds against
controller-runtime v0.24.1; that envtest accepts the hand-written CRD (regenerate with
`make manifests` if not); that the CI action versions and golangci-lint v2.12 behave as
expected; and the vLLM argument layout (`vllm serve <model>` is an assumption, flagged in
`backends.go`). Server-side-apply behaviour (no-op applies keeping resourceVersion, pruning of
removed list items, ownership moving to another manager) is well documented Kubernetes
behaviour, and the tests exist to prove it on your cluster rather than to trust it.

## Known limits of M1

- `accelerator` is validated and reported (`AcceleratorApplied=False`) but no device claim is
  created until the DRA milestone.
- Changing `autoscaling.minReplicas` does not rescale a running Deployment (see ADR 0003).
- Ollama runs `ollama serve` but does not pull a model; the model-cache milestone does that.
- No events are emitted; the conditions are the record.
